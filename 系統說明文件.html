重要防砂構造物處置情形登錄系統

功能開發規格書

1. 系統全面概述與架構

本系統主要用於管理與記錄「重要防砂構造物」在巡查後的處置狀態。系統採用單頁面/分頁籤應用 (SPA / Tab-based) 架構，全功能分為兩大核心檢視區塊：

  • CD級列管追蹤 (頂層主檢視清單)：供使用者依照分署、FID、巡查評級等條件進行篩選，檢視所有被列管的防砂構造物清單。
  • 詳細資料區 (選取清單資料後進入)：包含兩個子分頁 (Tab)：
    • 巡查登錄表單：提供表單填寫、基本資料區、處置結果動態連動控制、R4 維修工程編號彈性調整，以及嚴格驗證的照片上傳功能。
    • 歷次紀錄：以唯讀清單形式展現該構造物過去所有的巡查處置歷史。

2. 頁籤與檢視邏輯管理 (View / Tab Control)

  • 主檢視層級切換：
    • #trackingView：預設為顯示狀態（包含查詢條件卡片與結果清單）。
    • #detailSection：預設隱藏 (display: none)。當使用者於主清單中點選某筆資料的「登錄」時，切換為顯示，並將 #trackingView 隱藏。
  • 詳細資料區子頁籤：
    • 內含 #formView (巡查登錄表單) 與 #historyView (歷次紀錄)。工程師需透過點擊切換控制，動態賦予主選單按鈕 .active 樣式。

4. 巡查登錄表單 (Detail Form View)

A. 填表基礎資訊

  • 填表人：#fillerName (Text Input，必填)
  • 填表日期：#fillerDate (中華民國民國日期組件，必填)

B. 基本資料區卡片

此區塊所有資料皆為唯讀模式 (Read-only)，並套用 .locked-input 樣式鎖定。

順序 欄位名稱 HTML ID / Element Class 呈現與控制邏輯
1所屬分署#formDivision唯讀文字顯示
2構造物編號#formStructureId唯讀文字顯示
3FID#formFid唯讀文字顯示
4 集水區 #formCatchment 唯讀文字顯示。前台程式需動態**擷取構造物編號的前綴文字**（例如：編號為 茄苳寮-10-A11-101，則系統自動擷取帶入 茄苳寮）。
5 巡查評級 .grade-readout

💡 備註：基本資料區卡片內容的所有欄位，均以最近一次的巡查內容為主。

C. 處置結果選取與前台連動控制

使用者透過 Radio Button 單選按鈕群組 (name="disposalGrade") 進行第一層大項選擇：

  • 業務硬性規則： 處置結果第一層選取器僅提供 C 與 D 兩個大項選項。
  • 當選取大項 C 時： 下方連動展開且限勾選細項單選鈕：R1、R2、R3、R4。其餘項目隱藏。
  • 當選取大項 D 時： 下方連動展開且限勾選細項單選鈕：R3、R4。其餘項目隱藏。
  • 面板連動展開規則： 不論大項選 C 或 D，只要細項勾選為 R4 規劃修復工程，前台必須動態展開修復工程設定面板 #r4Panel (套用 .visible 樣式)；若改選 R1~R3 則立即隱藏面板。
  • 處置結果說明欄位： #disposalDesc (TextArea，非必填)，獨立配置於處置結果選取區塊下方，供使用者輸入針對本次處置判斷的補充文字說明。

D. 修復工程設定面板 (#r4Panel) 與外部系統介接

當 R4 面板顯示時，允許使用者查詢外部工程資料並進行填報設定。

  • 修復工程編號： #repairCodeInput (Text Input) + 「查詢帶入」按鈕 (onclick="lookupRepairCode()")。
    • 驗證成功： 顯示結果區塊 #repairResult (套用 .visible)，於提示區呈現綠色成功文字，並執行資料預填。
    • 驗證失敗： 隱藏結果區塊，提示紅色錯誤訊息如 "查無此工程編號"。
  • 修復工程內容： #repairNameField (Text Input)。
    • 控制規則： 系統查詢成功後先自動預填帶入工程內容，但該欄位簡化並保持開放可編輯狀態 (Editable)，允許使用者手動修改與調整。
  • 修復工程進度 (Radio 單選彈性調整元件)：
    • 共包含 4 個進度項目：1. 尚未辦理、2. 工程發包、3. 施工進行中、4. 工程完工並驗收。
    • 控制規則： 系統依據外部工程系統抽回的階段狀態進行預設帶入勾選（僅能單選），但前台**仍維持編輯功能**，允許使用者因應最新實務現況隨時手動改選其他進度項目。橫列中內嵌的微型資料欄位（進度百分比、預定完工日期、工期天數、執行年度）於系統帶入時顯示。
  • 現況說明： #repairProgressDesc (TextArea)。
    • 控制規則： 整合配置於本修復工程面板內，並固定於**「工程進行照片或完工照片」的上方**。供填表人員輸入當前工程執行或停擺的具體辦理現況說明。
  • 擬辦工程說明欄位群 (本系統使用者自行填寫區域，皆為必填)：
    • 概估經費： #proposedBudget (Number Input，實務限制單位：千元，必填)。
    • 預計辦理日期： #proposedDate (民國日期元件，必填)。
    • 擬辦工程內容： #proposedContent (Textarea，必填)。

E. 巡查照片上傳模組與硬性檢核限制

包含固定結構的「基本巡查照片」兩個獨立上傳框 (#photoBox1, #photoBox2) 以及動態增刪、上限 3 張的「處置佐證相簿」（即工程進行照片或完工照片）。

⚠️ 照片上傳嚴格驗證邏輯（前台 Change 事件與後端 API 必須同步實作硬性攔截）：
  • 副檔名格式限制： 僅允許擴充副檔名為 .jpg、.jpeg、.png 之圖片檔案。
  • 檔案容量限制： 單張照片之檔案大小上限為 5MB。若容量超標或格式不符，前台必須以彈出視窗（Alert）警告並阻斷上傳行為，清除 File Input 內之暫存值。

F. 儲存送出控制與阻斷警示機制

⚠️ 新增儲存確認（前台 Submit 按鈕觸發事件）：

當使用者點選「儲存」按鈕時，前端 JavaScript 必須強制攔截表單提交，並彈出二次確認對話視窗（如 window.confirm 或系統客製化 Modal），提示精確訊息：

  • 「一旦儲存後，資料就無法修改，且會列入歷次紀錄，確定要新增儲存？」
  • 使用者點擊「取消」：中斷儲存行為，維持於當前編輯填報狀態。
  • 使用者點擊「確定」：始正式執行表單欄位檢驗並發送後端 API 進行資料儲存。

5. 歷次紀錄子頁籤 (History View)

當使用者切換至歷次紀錄子分頁時，前端以 Table 形式動態加載此構造物歷史資料。

🔒 權限與編輯限制業務宣告：

本子頁籤所顯示之歷史資料為「純讀取（Read-only）歸檔狀態」。歷次紀錄僅能檢視，在任何情況下皆不允許修改，本列表不提供編輯按鈕或即時編輯（Inline Editing）控制元件。

  • 列表呈現欄位： 列表必須嚴格遵循且僅包含以下 3 個欄位：
    1. 巡查日期 (顯示民國曆格式)
    2. 巡查評級 (依 C1/C2/D1/D2 動態渲染為評級 Tag)
    3. 處置結果 (顯示細項代碼與文字標籤，如 R1/R2/R3/R4)
